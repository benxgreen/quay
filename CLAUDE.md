# Quay – Device portal (BCP Council)

Context for Claude Code. Read this first, then the docs in `docs/`.

## What this is

Quay is an internal portal for BCP Council's Modern Workplace team, built to grow into one system that hosts the team's internal tools. The first area is the **Device portal** (working name devices.services.bcpcouncil.gov.uk, likely hosted at quay.internal.bcpcouncil.gov.uk or similar). It works alongside HaloITSM: Halo stays the ITSM system and asset register.

Services planned inside the portal:

| Service | Schema | Run by | Sends from | State |
|---|---|---|---|---|
| Laptop replacements | `lr` | Desktop Infrastructure | desktopinfrastructure@bcpcouncil.gov.uk | Fully specified, schema written |
| Smartphone replacements | `sr` | Governance & Compliance | ictgc@bcpcouncil.gov.uk | Only `sr.settings` so far |
| New starters | `ns` (later) | New starters team | – | Not started |
| Inactive Audit | – | – | – | Not started |

Laptop replacements replaces an Excel workbook plus twelve Power Automate flows. The full spec is `docs/laptop-replacement-spec.md`.

Quay is early: a design proof of concept going through approval phases. Its name follows on from **Harbour**, the council's existing public entry point for forms (also Next.js, on Azure App Service). Harbour had a question builder; Quay will need one too, so Harbour's version is the starting point for those requirements.

## Stack and decisions already made

- **Next.js** (App Router) with **TypeScript** (strict). `/app/api` mirrors the services, e.g. `/app/api/replacements/laptops/...`. Routes follow the mockups: `/my/...` for colleagues, `/manage/...` for the team (e.g. `/manage/replacements/laptops/cases`).
- **Tooling:** Biome for linting and formatting (Harbour's settings), Vitest + Testing Library + axe-core for tests (`tests/`), Storybook (`@storybook/nextjs-vite`, a11y addon set to fail on violations) with stories in `stories/`.
- **Every external call goes through a reusable client** in `lib/clients` (Halo, Power Automate, GOV.UK bank holidays). No ad hoc `fetch` calls to these from routes or components. Server-side only; secrets never reach the client. There is no Microsoft Graph client: Entra ID (Better Auth) is only for sign-in, and its object ID pairs with the Halo user (`portal.users.entra_object_id` → `halo_user_id`), so **staff details (name, username, job title, department, disabled accounts) come from Halo** (`lib/clients/halo/users.ts`). **Halo is one connection** (`halo`: the Halo site, e.g. https://halohub.bcpcouncil.gov.uk; API docs at `/apidoc`) with many requests. `lib/clients/halo/http.ts` signs in with OAuth2 client credentials (`HALO_CLIENT_ID`, `HALO_CLIENT_SECRET`, `HALO_SCOPE` in `.env`; token cached for its hour), reads with GET and updates with POST (Halo takes an array and updates records that have an `id`; there is no PUT), and explains 429s (700 requests per 5 minutes). `callHalo` runs one portal action's requests as one connection log entry listing them. Each part of the portal declares the requests it needs: staff details portal-wide (`lib/clients/halo/users.ts`, built: GET /Users then GET /Users/{id}, because only the single user has the department), and laptop replacements' report, stock, completion update (puts the new device In Service), old device returned and decommission in `services/replacements/laptops/lib/halo` (mock only; the planned endpoints are in its comments). Power Automate is a plain webhook, ported from Harbour (`lib/clients/webhook`: URL checks, two retries with 1s/2s backoff) and wrapped by `lib/clients/email`.
- **Clients log every call** through `callExternal` in `lib/clients/connection-log.ts`, which writes `lr.connection_log` and throws `ExternalCallError` on failure. Each client names its connection (`halo`, `email_webhook`), and the log summary says which call it was; URLs come from `portal.connections` via `getConnectionUrl`. `HALO_CLIENT` / `EMAIL_CLIENT` choose `mock` (default) or `http`; `MOCK_FAILURES=halo,email_webhook` makes mock calls fail to show the Failed banner. Mock data is in `mocks/`. Use `externalFirst` (`lib/external-first.ts`) for any action that calls out then saves, with `recordFailure: journalFailure(…)` (`services/replacements/laptops/lib/journal.ts`) so a failed attempt is still journaled.
- **Auth:** Better Auth (`lib/auth/better-auth.ts`) with its built-in Microsoft Entra ID provider (not Auth.js). SSO only, **cookie-only sessions** (stateless mode, no database): `portal.users` is the only user table. Better Auth only proves who someone is: the session carries their Entra object ID, which a `customSession` plugin reads from Better Auth's encrypted account cookie (not `additionalFields`, which stateless mode drops, and not Better Auth's account list, which is in memory; `tests/lib/better-auth.test.ts` proves it). No Graph scopes or profile photo.
  - **Sign-in:** `/sign-in` ("Signing you in to Quay") sends people straight to Microsoft; Microsoft returns to `/auth/complete`, which calls `finishSignIn`: find the Halo user by Entra object ID, refuse anyone not in Halo or disabled, upsert `portal.users` from Halo (`upsertUserFromHalo`, matching on object ID, Halo ID, then email) and go to `returnTo` (`safeReturnTo`), or `/manage` for anyone with a role, else `/my`. A refusal ends the session and shows "We could not sign you in" with a reference also written to the server log.
  - **Development sign-in:** until the Entra app registration exists (`ENTRA_*` unset, or `AUTH_MODE=dev`), `/sign-in` redirects to `/auth/dev`, which lists the mock Halo users to sign in as, through the same `finishSignIn`. `/auth/dev` is a 404 in Entra mode and refused in production.
  - **Current user and guards:** `getCurrentUser()` reads the person and their roles from `portal.users` once per request (so role changes apply at once). `requireUser()` and `requireRole(ACCESS.x)` (`lib/auth/guards.ts`) guard layouts, pages and **every server action** (layouts don't re-run on every navigation). Who can open what is in `lib/portal/access.ts`: any role for `/manage`, a service's team or admin role for the service, its admin role for its Settings, Administrator for Users and Portal settings. Everyone who signs in can use the portal: a page their roles don't cover redirects to `/my` (no "no access" pages). `proxy.ts` sends anyone without a session cookie to sign in and passes the path on for `returnTo`. The Menu only lists what someone can open.
- **Database:** PostgreSQL 16 on Azure Database for PostgreSQL Flexible Server, behind PgBouncer (transaction mode). Locally the same in Docker (`compose.yaml`, `npm run db:up`, `db:setup`, `db:migrate`, `db:seed`; `db:reset` rebuilds everything; see `db/README.md`). All database access goes through `lib/db` (`query`, `queryOne`, `withTransaction`, `describeConstraintError`); `date` columns come back as `YYYY-MM-DD` strings. Working-day rules are in `lib/dates/working-days.ts` (mirroring the SQL functions), bank holidays in `lib/clients/bank-holidays`, and today's London date and the dev "as if today is" override in `lib/clock.ts`. Plain SQL with `pg`, no ORM. Numbered migrations run by `db/scripts/migrate.mjs`. One database `quay` (renamed from the schema doc's `devices`, because Quay will hold more than the Device portal), one schema per service. Full schema: `docs/database-schema.md`. (Dataverse was considered and rejected.)
- **Hosting:** Azure App Service (Linux), like Harbour, deployed from the VS Code Azure Resources extension rather than CI/CD. **Don't use `output: 'standalone'`.** Harbour (`../bcp-fms`) deploys a zip with `SCM_DO_BUILD_DURING_DEPLOYMENT=true` in `.deployment` so App Service builds it; expect the same here.
- **Emails:** the portal renders subject + HTML + text and POSTs them to one Power Automate flow that only sends. No logic or templates live in Power Automate.
- **Scheduled jobs:** timer-triggered calls (Azure Functions timer or a cron-triggered route) to secured, idempotent job endpoints. All 9am jobs run together.
- **Error tracking:** Azure Application Insights preferred (self-hosted GlitchTip as the alternative); not Sentry.
- **Build order:** interface first (likely in Storybook) against mock data, then wire in the real APIs.

## Frontend conventions

- GOV.UK Design System patterns throughout, WCAG 2.2 AA. Use real `<button>`, `<a href>`, `<label>`; error summaries; confirmation pages for anything that sends an email or can't be undone; red warning button for destructive actions.
- The team has its own component library, the **BCP Council Design System**, in Harbour: `../bcp-fms/components/ui`. It will be compared with the portal's components to form the final, expanded library, so build components so they can be swapped or merged. Every difference from Harbour goes in `docs/design-differences.md`.
- **Vanilla CSS with BCP-prefixed class names** in Harbour's format `bcp-[component]-[subname]--[child]` (e.g. `bcp-button--secondary`, `bcp-summary-list-row`). No Tailwind, no CSS Modules. Tokens live in `components/ui/bcp-design-system.css`.
- **Component structure (Harbour's standard):** one kebab-case folder per component holding exactly `index.tsx` and `<name>.css`, the CSS imported in `index.tsx`. Generic UI components in `components/ui/` (button, accordion, table, step list…); patterns that combine them in `components/patterns/` (filter panel, journal, lookup field, add another…), following the mockups' Components and Patterns pages; page frames in `components/layouts/`; service components grouped by service in `components/service/<service>/` (e.g. `replacements/type-tag`). Stories mirror this in `stories/` and Storybook (Components, Patterns, Service, Layouts); tests in `tests/`. Name components for what they are, not the service (StepList, not ReplacementSteps). Prefer server components; mark client components only when they need state.
- The team's Markdown library is Harbour's, ported as one parser (`lib/markdown/parse.ts`) with three outputs: `components/ui/markdown` for page content and FAQs, `lib/markdown/email-html.ts` (the mockup's inline styles, for Outlook) and `lib/markdown/plain-text.ts`. Use it rather than adding another. Emails are rendered by `lib/emails/render.ts` (variables filled in one pass: blank when sending, left as written in a test; the message placed in the portal email template's `{content}`, `{preheader}` and `{team_name}`). Each service's variables and email list are in code, e.g. `services/replacements/laptops/lib/emails`.
- **The mockups canvas is the source of truth for visuals.** The Components page defines each component; where the Laptop replacements screens consistently differ, the screens win. Record contradictions in `docs/design-differences.md` rather than guessing.
- **Components in `components/ui/` are a design system:** generic props and tokens (Harbour's `Container`: `width="full"`, `contentWidth="half"`), never named after a page type or service. Page types live in `components/layouts/` (TeamLayout/TeamPage, ColleagueLayout/ColleaguePage), matching the mockups' page templates.
- Layout: team pages use the `full` container (1260px, 60px gutters, 20px on phones); colleague pages the `large` container (1100px) with one column up to 760px, question pages 680px. Pages with a sidebar use `SidebarLayout` (sidebar up to 320px), shown only when it has something to act on. Phones are `max-width: 640px`.
- The header shows the council logo only. The team header's Menu needs JavaScript; there is no no-JavaScript version.
- Long lists use a secondary "Show more" button with "Showing X of Y" (announced to screen readers, focus moves to the first new row) rather than pagination.
- Times are always written in full, "10:00am", "12:00pm", never "10am" or "midday", through `formatTime` (`lib/dates/format.ts`), in pages and emails alike.
- Collection vs Session: blue "Collection" tag, purple "Session" tag, always colour plus the word.
- Colleague-facing pages say "software", never "business applications". Colleagues never see the case reference.

## Database rules that bite (PgBouncer transaction mode)

- Schema-qualify every table (`lr.cases`, `portal.users`). Never rely on `search_path`.
- No session features from the app: no `SET`, `LISTEN`, advisory locks or temp tables. The one exception is `SELECT set_config('portal.acting_user', $1, true)`, which is transaction-scoped.
- Multi-step writes go through one client in a `BEGIN`/`COMMIT` transaction.
- Normal parameterised queries (`$1`); never pass `name:` (named prepared statements).
- The app connects as `portal_app` on port 6432. Migrations connect as `portal_migrator` on port 5432 only.
- Never edit a migration that has run; add a new numbered file. New tables need no grants (default privileges cover them).
- Map constraint names in `err.constraint` to friendly messages (table in the schema doc).

## Core business rules (enforced server-side, in the service layer)

- **External calls first:** any action that calls Halo, the decommission hook or Power Automate makes the call before anything is saved. Success → write to the DB and journal, green success banner. Failure → nothing changes, red "Failed" banner with what failed and a link to the Connection log. Every call is written to `lr.connection_log`.
- Every action and every email writes a journal entry, including one whose external call failed: that entry has `outcome = 'failed'` and shows a red Failed tag, and nothing else changes (migration 0015). Journal entries are never edited or deleted. Cases are never deleted; archiving is a date filter (one month after `closed_at`), not a status.
- Working days are Monday–Friday excluding England and Wales bank holidays (GOV.UK bank holidays feed, cached daily). Note `lr.add_working_days` in SQL only knows weekdays, so the app should pass bank-holiday-aware dates where it matters.
- In development, jobs can be run on demand with a "run as if today is" date; the app passes that date to queries rather than changing the database clock.

Decisions made after the handoff (29 Oct 2026), which override the spec and schema doc:

- Migrations 0001–0012 are copied exactly from the schema doc into `db/migrations/`; **0013** (`db/migrations/0013_steps_connections_and_fixes.sql`) holds the post-handoff changes: step completion columns (`device_prepared_at/by`, `software_prepared_at/by`), `lr.imports.file_name` nullable, no CHECK on `lr.connection_log.connection`, `lr.software.sort_order` dropped, `portal.connections` for URLs, `add_working_days(d, 0)` returning `d` plus a bank-holiday-aware 3-argument form, a `p_bank_holidays` parameter on `email_forecast`, and `portal_app` losing UPDATE/DELETE on `lr.journal_entries`, `lr.device_journal` and `portal.user_role_history` and DELETE on `lr.cases`. From here on `db/migrations/` is the source of truth for the schema, not the doc.
- **Connections:** URLs (webhook links, API base URLs) are in `portal.connections` and editable by Administrators; secrets are in `.env`. Each client declares its own connection name and logs every call through one shared connection logger.
- No per-user preferences: filters and columns live in the URL only, not "remembered per user".
- Sessions (stage 5): cancelling a session saves first (bookings Cancelled, cases to Rebook required, session Cancelled, journal), then sends each "Session cancelled" email; a failed email is journaled with a Failed tag and listed in a Failed banner, and the cancellation stands. This is the one exception to external calls first, because a batch of emails can't be all-or-nothing. A cancellation restarts booking reminders from zero (`reminders_sent = 0`). A session's type can't change while anyone is booked on it. Emails go through `sendCaseEmail` (`services/replacements/laptops/lib/emails/send.ts`), which renders, sends, and writes `lr.email_sends` and the journal whatever the result. Email links use `PORTAL_URL`; the signed case token comes in stage 9.
- Import (stage 6): the latest Halo report is kept in `lr.halo_report` (migration 0016) with each assigned user's Halo check, and only "Refresh from Halo" (or the first visit) calls Halo, as one logged call for the report and one for every user. Hidden: an open or completed case, or a previous replacement (by asset ID or serial); a withdrawn case doesn't hide the laptop. Needs attention: no assigned user, not in Halo's staff directory, or a disabled account. Adding to the queue creates Queued cases (and portal users from Halo) in the order selected; the type isn't preselected. Queue order is `queued_at`; Move to front sets it before the first; Remove withdraws the case (`withdrawn_reason` "Removed from the invitation queue") behind a confirmation page; "Added" shows `created_at`. Estimated invitation dates use the daily limit, 9am on working days and bank holidays (`invitation-dates.ts`).
- Cases (stage 7): case pages are `/cases/LR-000123`. Every action has its own confirmation page (`/cases/LR-000123/<action>`) and is checked again in the service (`availableActions`): resend booking details, resend invitation (an Unbooked case goes back to Pending, flag cleared, reminders restarting), cancel booking, record did not attend (from the booking's day), flag (only Queued, Pending or Rebook required), clear flag, change type (until there's a booking) and withdraw (laptops admin only; cancels the booking, returns the box to stock, clears any flag, sends nothing). Actions that email send first and change nothing if the email fails (the attempt is still journaled, with a Failed tag). Cancel and did not attend restart reminders from zero. A manual case goes into the queue and lands on the queue page. Steps are shown read-only until stage 8; Book on behalf and custom appointments come in stage 9.
- Case steps and Stock (stage 8): the steps are worked on the case page (`services/replacements/laptops/lib/steps.ts`). Allocation copies the preparation checklist for that box; checklists save only on "Save…" or the primary button, which also confirms once everything is ticked (an early confirm still saves the ticks); each save writes one journal entry; leaving with unsaved ticks warns (`components/patterns/checklist`). "Update to latest list" brings a started checklist in line with Settings, keeping saved ticks. Complete replacement, Mark old device as returned and Decommission call Halo first; if Halo fails nothing changes, the attempt is journaled with a Failed tag and the case shows the mockup's Failed banner. After completion the "Device issued" email is sent (a failed email doesn't undo it). Unallocate (with an optional reason) clears the device preparation and the software ticks, which must be redone on the new box; Reopen keeps ticks. The latest Halo stock list is kept in `lr.halo_stock` (migration 0017), like the Import report; issued boxes are never offered again. The device page has its allocation history and a journal with notes.
- Colleague journey (stage 9): /my and /my/replacements/laptop, matched on the signed-in person; email links carry a signed case token (`booking-link.ts`). Booking saves first, then emails; capacity is enforced by the database. "Not available" on Rebook moves the case to Unbooked with reminders paused; an availability request flags it "Unavailable for sessions". The team can book on behalf (inside the lead time), rebook, change software after the lock (an override) and book custom appointments. Add a case asks "What happens next?": the queue, or book on their behalf straight away. Queued cases are hidden from colleagues.
- Scheduled jobs (stage 10): seven jobs in `services/replacements/laptops/lib/jobs` (send invitations, booking reminders, rebook reminders, session reminders and return reminders, then purging the connection log and email counts), run in that order by one 9am timer calling `POST /api/replacements/laptops/jobs` (or `/jobs/<job>` for one) with `Authorization: Bearer <JOBS_SECRET>`. The spec's "Close sessions" isn't a job: yesterday's still-Booked bookings are a query for the Bookings dashboard. Every run is in `lr.job_runs`, and every case it emailed in `lr.job_run_cases` (migration 0018). The jobs use the same rules as `lr.email_forecast` and skip anyone already emailed by that job for the day, so a re-run never sends twice. A failed email is journaled with a Failed tag and changes nothing (a failed invitation leaves the case Queued); the 3rd booking or rebook reminder flags the case "3 reminders" unless it is already flagged. Settings › Scheduled jobs (laptops admin) shows each job's last run and the job log; in development it can run the jobs on demand "as if today is" a date (also `?asOf=` on the endpoint).
- Bookings dashboard (stage 11): one page, `/manage/replacements/laptops/bookings`, with the view, date and filters in the URL (`view=day|week|month|all|incomplete`, `date`, `q`, `type`, `kind`, `device`, `software`, `past`). Queries are in `services/replacements/laptops/lib/bookings.ts`; search and the "not prepared" filters narrow the people, and hide sessions with nobody matching. The spec's "Close sessions" job is `bookingsToReview`: bookings from past days still Booked, shown in a note on every view with a review modal (`components/service/replacements/booking-review`) that refreshes when you come back to the tab. The Incomplete bookings view lists the same bookings with the dashboard's filters. Book on behalf is only offered to a case waiting for a booking (Queued, Pending, Unbooked, Rebook required); a refused booking says why rather than calling the date full. `ShowMoreTable` shows every row when printing.
- Users pages: everyone in the directory is listed from Halo (paged); a role filter or "Portal users only" lists portal users from the database, so "Colleague (no role)" means portal users without a role. A user's page is `/manage/users/{Halo user ID}`, so it works before they have a portal user. Saving a role creates the portal user. The last Administrator's role cannot be removed.
- Journal stays in `lr` (`lr.journal_entries`).
- Session defaults: 10:00 for both types (the mockup's 09:30 for Session is out of date).
- The software list is always sorted alphabetically.
- "I am not available for any of these dates" moves the case to Unbooked with reminders paused.
- Case replacement steps are always open, with no Show/Hide or "Show all steps" (the spec's Show/Hide is out of date).
- Column choices on lists are not remembered: they live in the URL like the other filters.
- The mockups' Laptop replacements page is the most up-to-date source for screens.
- Weekly emails (booking, rebook and return reminders) go on their weekday; when that day is a bank holiday they go on the next working day. The 9am jobs and `lr.email_forecast` both decide this with `lr.is_weekly_send_day(day, weekday, bank_holidays)` (migration 0014), so the forecast matches what is sent.
- Migration 0015: one `halo` connection replaces `halo_import`, `halo_stock` and `decommission_hook`; `portal.users.halo_user_id` pairs each user with Halo (staff details come from Halo, not Graph); `lr.journal_entries.outcome` marks failed attempts.

Where the spec and schema disagree, the schema reflects later decisions (for example: flag at the 3rd reminder, session status `Full` is derived not stored, software arrays are `text[]` not `jsonb`, the case's person is `user_id` with `halo_assigned_user_id` for reference). Flag any other conflicts rather than guessing.
